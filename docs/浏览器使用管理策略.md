# 浏览器使用管理策略 — 常驻单例、生命周期与防互搏

> **English summary**: Browser management is its own engineering discipline in
> large-scale crawling: the browser is the heaviest process you manage, and
> getting its lifecycle wrong produces pathologies that look like site problems
> — launch/kill fight loops (8–18 build-teardown cycles per minute from
> concurrent workers), profile-corruption crash loops, tab leaks that push
> memory pressure, and singleton hijacking of personal browser instances. This
> doc distills the strategy converged from a full 144-school run over 5,000+
> department sites: a 3-kind browser asset model (resident CDP singleton /
> DrissionPage window pool / on-demand temporary instances), four lifecycle
> rules (flock-gated singleton launch with probe-and-reuse, watchdog-only
> lifecycle ownership, explicit project-Chromium binding for every self-start
> fallback, idle reaping), resource governance (tab-leak and orphan reaping,
> 3-tier load guard, per-run budgets), isolation from the user's personal
> browser (independent Chromium binary + profile), and an audit discipline
> (browser_ops.log; "8+ launches/min = fight loop, trace the PPID chain").

> 本文档沉淀本框架在 **144 校全量运行、5,000+ 院系站点**采集实战中收敛出的
> 浏览器使用管理策略。所有机制以 `util/` 下代码为准。

## 定位：为什么浏览器管理是采集工程的独立课题

反爬对抗与 JS 渲染站点必须用浏览器，而浏览器是采集链路中**最重的进程**。
管理不当的代价常常伪装成「站点问题」：互搏循环、profile 损坏 crash-loop、
tab 泄漏推高内存、单例劫持个人浏览器。这些问题不会出现在功能测试里，
只会在长跑中爆发。本策略的核心思想：**生命周期收权给单一管理者，
启动路径加锁探活，一切操作留痕可追**。

## 一、资产模型：三种浏览器各司其职

| 资产 | 代码位置 | 用途 | 生命周期归属 |
|---|---|---|---|
| **CDP 常驻单例**（`CDP_BASE_URL`） | `util/cdp_util.py` | Playwright 复用通道、JS 全渲染 | **watchdog 唯一管理** |
| **DrissionPage 窗口池** | `util/drission_pool.py` | 渲染兜底窗口池（窗口×标签） | 池管理 + 空闲回收 |
| **按需临时实例** | 请求链自启兜底 | 一次性渲染任务 | 用完即杀（开发期 atexit 清理） |

三种资产绝不混用：常驻的不被业务进程杀，临时的不许长期残留。

## 二、生命周期铁律（互搏循环根治沉淀）

1. **常驻浏览器 = 跨进程单例**：启动段必须持 **flock 文件锁**，锁内先探活
   （读 `/json/version`）——见活实例直接复用，**严禁无条件 pkill**。
   进程内 `threading.Lock` 挡不住多 worker 子进程，必须是文件锁。
2. **生命周期唯一归属 watchdog**：业务进程退出**不得**杀常驻浏览器。
   「谁退出谁杀」= 多进程并发时互相杀，历史上表现为 8-18 次/分的
   建窗↔杀窗互搏（Connection reset by peer 反复）。
3. **任何浏览器自启兜底必须显式 `set_browser_path`（项目独立 Chromium）**：
   连接失败自动拉起时，默认会使用系统浏览器——必须绑死项目 Chromium
   （`browser_lifecycle._resolve_project_chrome()` / `PROJECT_CHROME_BIN`）。
4. **空闲回收**：`BROWSER_IDLE_REAP`（秒，0=关闭）无活动自动回收；
   `util/browser_lifecycle.py` 默认 1800s，与 `browser_ops.py` 审计日志共用
   同一环境变量口径。

## 三、资源治理

- **窗口池上限**：`DRISSION_MAX_WINDOWS` × `DRISSION_MAX_TABS_PER_WINDOW`
  封顶，超限排队不爆窗口。
- **tab 泄漏回收**：spider 超时被杀时 page 永不 close——同 URL 长时间不变
  即关（`reap_cdp_tabs.py` 思路，watchdog 周期执行）。
- **孤儿 driver 回收**：只杀 `ppid=1` 的遗留 CDP 连接，绝不误伤正常 worker。
- **三档负载守卫**：`util/resource_guard.py` 绿/黄/红按系统负载降并发；
  `util/browser_budget.py` 给每个院系限浏览器预算。
- **profile 卫生**：crash-loop 的常见根因是 profile 缓存损坏
  （日 6+ 次崩溃、缓存膨胀到 1GB+）——**清 profile 重建即愈**，别改代码。

## 四、与个人浏览器的隔离

- 项目浏览器一律使用**独立 Chromium**（独立二进制 + 独立 user-data-dir），
  与用户日常浏览器是完全不同的实例。
- 理由：同 bundle ID 的单例转发会劫持——项目空 profile 实例先启动时，
  用户点开自己的浏览器会被转发进项目实例（表现为「数据不见了」，实为
  空 profile）；反向亦然。独立二进制从机制上消除这一整类问题。
- 代码防线：`browser_lifecycle.personal_chrome_running()` 检测 +
  `_resolve_project_chrome()` 路径解析，任何自启路径都过这一层。

## 五、审计纪律

- **`browser_ops.log` 全操作留痕**：launch/destroy/tab_open/tab_close/
  reap/refuse 事件带时间戳与 PID（`util/browser_ops.py`）。
- **互搏信号**：采集期「8+ 次/分 launch」= 互搏。排查顺序：
  1. `ps` 全树找调试端口进程 → 2. `ps -o ppid` 追父链定位触发进程 →
  3. browser_ops.log 时间线数频率 → 4. **修生命周期（锁/复用/不杀）而非加清理**。

## 六、关键事故与根治（实测教训表）

| 事故现象 | 根因 | 根治 |
|---|---|---|
| 建窗↔杀窗互搏 8-18 次/分 | 多 worker 并发「检查→pkill→拉起」互相杀；atexit 谁退谁杀 | flock 启动锁 + 锁内探活复用；生命周期收归 watchdog |
| 常驻浏览器日 6+ 次崩溃 | profile 缓存损坏（并发双 Popen 写同一 profile） | 启动锁防并发写 + 清 profile 重建 |
| CDP 池静默失效 | Chrome 重启只绑 `::1`（IPv6），127.0.0.1 探活全失败 | 启动参数强制 `--remote-debugging-address=127.0.0.1` |
| swap 持续推高 | spider 超时被杀，page 永不 close，tab 无限累积 | 同 URL 超时回收器 + watchdog 周期执行 |
| 用户浏览器被「劫持」 | 同 bundle ID 单例转发进项目空 profile | 独立 Chromium（不同 bundle ID + 独立 profile） |
